    项目维护参考¶

    首次上传请先按首页快速开始逐步操作。本页保留完整维护规范、命令说明、标准命名、冲突处理和验收要求，供需要时查阅。

    章节入口：密码算法 · 密码协议 · 密码产品 · 密码测评。阅读时可以使用上方搜索框，也可以按章节导航浏览文章。

    项目 地址或位置
    源码仓库 Loora1N/GM-crypto-assessment-wiki
    在线知识库 密评标准知识库
    文档目录 项目中的 docs/
    导航配置 项目根目录中的 mkdocs.yml
    主分支 main
    本地预览 启动后以终端打印的地址为准，默认带 /GM-crypto-assessment-wiki/ 前缀

    [!important]

    日常上传顺序：同步项目 → 新建个人分支 → 编写文章和整理图片 → 修改导航 → 本地构建与 serve 检查 → Git 提交 → 推送分支 → 发起 Pull Request → 合入并确认发布。推送失败时，先在协作群同步，再排查和重试。

    1. 所有人必须遵守的规范¶

    1. 文章最外层分类固定为密码算法、密码协议、密码产品、密码测评。每章内按二级主题分类，再放置具体文章，不自行增加第五个文章章节。
    2. 每篇正式文章独立建立文件夹，文章 .md、图片和随文附件全部保存在这个文件夹内。推荐图片统一存放在文章下的 assets/ 子目录。
    3. 所有项目变更通过 Git 管理，包括文章、图片和 mkdocs.yml。不要用下载 ZIP 后覆盖文件的方式代替版本管理。
    4. 每次 push 前必须对准备上传的最终内容运行 mkdocs serve，打开浏览器检查无误。只看 Typora 预览、只运行构建命令，均不能代替这一步。
    5. push 失败必须在协作群同步失败信息，保留本地文件和提交，按本手册排查；未确认原因前不强制推送。
    6. 标准类文章必须写清标准编号、完整标准名称、版本年份及引用出处。标题、目录名、文件名、导航中的编号保持一致。
    7. 日常使用个人分支并通过 Pull Request 合入 main。合入前由维护者检查分类、文件路径、内容来源和构建结果。

    首页、docs/maintenance/ 中的维护参考和各章的 index.md 是项目说明页，不新增文章章节；正式笔记仍须归入四个文章章节并遵守“一篇文章一个目录”。docs/assets/ 是网站主题的公共资源目录，文章配图不要放进这里。

    2. 目录、文章和标准命名¶

    2.1 四个章节与二级分类¶

    网站章节 一级目录 二级分类约定
    密码算法 docs/algorithm/ 对称密码算法、非对称密码算法、杂凑算法
    密码协议 docs/protocol/ 安全传输协议、认证协议、密钥交换协议
    密码产品 docs/product/ 智能密码钥匙、服务器密码机、密钥管理设备
    密码测评 docs/assessment/ 测评基础、测评实施、案例与学习笔记

    有实际文章时，再把对应二级分类和文章登记到 nav。只有分类规划而没有文章时，在章节概览中说明即可，不添加指向不存在文件的导航。确实需要新增二级分类时，先与维护者确认归属和名称。

    正式文章的路径形式为：

    docs/章节目录/二级分类/文章目录/文章文件.md
docs/章节目录/二级分类/文章目录/assets/图片文件.png

    下面是一篇新标准笔记的目录示意，其中 GBT35291-2017… 是上传流程的演示文章，需要作者实际创建：

    GM-crypto-assessment-wiki/

│   ├── assets/                   # 网站公共主题资源
│   ├── algorithm/
│   │   └── index.md              # 密码算法章节概览
│   ├── protocol/
│   │   └── index.md              # 密码协议章节概览
│   ├── product/
│   │   ├── index.md              # 密码产品章节概览
│   │   └── 智能密码钥匙/

    assets/ 在文章自己的目录中，符合“md 和图片同属一个文章目录”的要求。已有文章采用 文章名.assets/ 的，也可保留；其图片路径必须与实际目录名一致。Git 不保存空目录，图片目录暂时为空时没有出现在提交中属于正常情况。

    2.2 标准类文章编号¶

    项目用于目录、文件名、标题和导航的编号格式统一如下：

    类型 项目编号格式 格式示意
    国标 GBT + 原标准数字编号 + - + 四位年份 GBT12345-2017
    行标 GMT + 原标准数字编号 + - + 四位年份 GMT12345-2026

    上述两个编号是格式示意，不代表本项目已收录对应标准。保留真实标准号的所有数字及前导零，例如 GM/T 0017-2023 在项目中写作 GMT0017-2023；不要随意补位、删掉前导零或改动年份。

    真实标准示例：GB/T 35291-2017 的完整名称为“信息安全技术 智能密码钥匙应用接口规范”。在项目中使用：

    • 文章目录：GBT35291-2017信息安全技术智能密码钥匙应用接口规范/。
    • Markdown 文件：GBT35291-2017信息安全技术智能密码钥匙应用接口规范.md。
    • 一级标题：# GBT35291-2017 信息安全技术 智能密码钥匙应用接口规范。
    • 导航名称：GBT35291-2017 信息安全技术 智能密码钥匙应用接口规范。
    • 正文元信息同时保留正式编号 GB/T 35291-2017 和项目编号 GBT35291-2017，方便核对。

    标准标题不只写“技术规范”“第7章”或“某国标”，也不只写编号。只整理部分条款时，在完整编号和名称后补充笔记范围，例如“第7章学习笔记”。普通学习笔记可以用“APDU解析”等内容名称，但引用标准时仍须交代编号和完整名称。

    2.3 文件名与版本¶

    • 同一标准的不同年份应建立不同文章目录，避免新版本覆盖旧版本。
    • 文章目录名与 .md 文件名建议一致；一级标题可以为阅读方便加入空格。
    • 图片推荐使用 interface-example.png、command-header.png 等简洁名称，避免空格及大小写混用。
    • Windows 文件名不要包含 /、\、:、*、?、"、<、>、|；这也是目录中不用 GB/T、GM/T 形式的原因。
    • 文件名、图片名及配置中的大小写必须一致；Windows 本地可能容忍大小写错误，GitHub 的 Linux 构建环境会区分大小写。

    3. 第一次使用：安装工具和设置 Git¶

    本手册的命令均用于 Windows PowerShell。打开开始菜单，搜索并启动 PowerShell。代码块中的命令按行执行，不要复制终端的 PS C:\...> 提示符。

    需要 Git、Python 3.12、浏览器，以及 Typora 或其他 Markdown 编辑器。先确认自己有 GitHub 账号，并请仓库维护者开通写入权限；可以下载公开仓库不代表可以向仓库推送。

    3.1 安装 Git 和 Python¶

    如果 Windows 已提供 WinGet，可执行以下命令。安装时按工具提示完成授权或安装选项，不需要自行关闭系统保护：

    winget --version
winget install --id Git.Git --exact --source winget
winget install --id Python.Python.3.12 --exact --source winget

    已经安装相应工具的同事不用重复安装。若 winget 不可用，从 Git for Windows 官网 和 Python Windows 下载页 安装；本项目使用 Python 3.12，安装时保留 Python 启动器，并按安装器选项添加命令行支持。

    安装结束后关闭并重新打开 PowerShell，检查：

    git --version
py -3.12 --version

    两条命令应分别显示 Git 和 Python 3.12 的版本。若提示找不到命令，先检查安装或重新打开终端，不继续执行后续步骤。

    3.2 配置提交身份¶

    把下面的姓名和邮箱替换成自己的信息。邮箱建议与自己的 GitHub 账号关联；这些信息用于标记提交作者，不是登录密码。

    git config --global user.name "张三"
git config --global user.email "zhangsan@example.com"
git config --global core.quotepath false
git config --global --get user.name
git config --global --get user.email

    core.quotepath false 让 Git 状态输出中的中文路径更容易阅读。首次通过 HTTPS 推送时，按 Git 凭据管理器提示在浏览器中登录有仓库权限的 GitHub 账号。

    4. 第一次使用：获取项目¶

    下面把仓库放在当前用户的“文档”目录中。可以使用其他工作目录，但后续命令必须进入同一个仓库。

    New-Item -ItemType Directory -Force -Path "$env:USERPROFILE\Documents\GMwiki-work"
Set-Location "$env:USERPROFILE\Documents\GMwiki-work"
git clone https://github.com/Loora1N/GM-crypto-assessment-wiki.git
Set-Location .\GM-crypto-assessment-wiki
git remote -v
git branch --show-current
git status

    检查结果：origin 指向上述仓库，当前分支为 main，工作区没有未提交改动。已经克隆过的同事，直接进入原项目目录，不要重复克隆到项目内部，也不要重新运行 git init。

    本手册后续命令都在项目根目录执行，即能看到 mkdocs.yml、requirements.txt 和 docs 的位置：

    Get-Location
Get-ChildItem

    如果提示“not a git repository”或找不到 mkdocs.yml，先用 Set-Location 进入正确目录。

    5. 第一次使用：建立本机 Python 环境¶

    在项目根目录执行：

    py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m mkdocs --version

    本手册直接使用虚拟环境中的 python.exe，不要求激活虚拟环境，也不需要修改 PowerShell 执行策略。只有第一次使用需要创建 .venv；之后若 requirements.txt 更新，重新执行安装依赖命令即可。

    .venv/、site/、site-offline/ 已由 .gitignore 排除，不能作为文章源码提交。不要把系统 Python、虚拟环境或构建目录复制给同事代替安装。

    6. 每次新增或修改文章：同步并新建分支¶

    先保存编辑器中的文件，再查看当前分支和工作区：

    git branch --show-current
git status

    只有工作区干净且没有未完成的合并时，才执行下面的同步命令。如果还有上一项工作的改动，先在原分支完成提交与上传，或请维护者帮助保留改动，不直接丢弃文件。

    git switch main
git pull --ff-only origin main
git switch -c docs/zhangsan-gbt35291-2017
git branch --show-current

    pull --ff-only 用于更新本机 main；失败就停下来检查，不继续基于旧版本编写。switch -c 创建并切换到新的个人分支。示例分支名请替换成自己的姓名拼音和任务名称，例如 docs/lisi-apdu-update；每项新任务使用不同名称。

    如果同一个任务的分支已经存在，继续这个分支时使用 git switch docs/zhangsan-gbt35291-2017，不要再次使用 -c。

    7. 新建文章目录、Markdown 与图片¶

    7.1 新建目录和文件¶

    以下以密码产品 → 智能密码钥匙 → GBT35291-2017 标准学习笔记为例。根据自己文章的分类和名称替换路径，各处必须一致。

    New-Item -ItemType Directory -Force -Path "docs\product\智能密码钥匙\GBT35291-2017信息安全技术智能密码钥匙应用接口规范\assets"
New-Item -ItemType File -Path "docs\product\智能密码钥匙\GBT35291-2017信息安全技术智能密码钥匙应用接口规范\GBT35291-2017信息安全技术智能密码钥匙应用接口规范.md"

    文件已存在时不要重新新建，直接用 Typora 打开并编辑。请保存为 .md 和 UTF-8 编码，检查文件没有误命名为 .md.txt。

    也可以在资源管理器中建立相同目录；命名和存储要求不变。新建文章时不把所有笔记平铺在章节根目录，也不把多个独立文章塞进同一个图片文件夹。

    7.3 图片必须随文章保存¶

    把本篇文章的图片复制到自己的 assets/ 目录，再插入图片链接。在 Typora 的图片设置中，将插入图片后的行为设置为复制到当前文章目录内的相对图片目录，例如 ./assets；具体选项可参考 Typora 图片说明。

    Markdown 中的正确写法：

    ![接口示意图](assets/interface-example.png)
![命令头结构](./assets/command-header.png)

    以下写法不能提交：

    ![图](C:\Users\张三\Desktop\image.png)        # 仅作者本机存在
![图](file:///C:/Users/张三/Desktop/image.png) # 本机绝对路径
![图](.\assets\image.png)                   # Windows 反斜杠
![图](/assets/image.png)                     # 指向网站根目录

    PowerShell 文件路径可以使用 \；Markdown 图片路径和 YAML 导航路径统一使用 /。 图片路径是相对于当前 .md 文件的，不是相对于项目根目录，所以这里不用写 docs/。

    Windows 用户尤其要检查 Typora 自动生成的链接，把图片链接中的反斜杠 \ 改成正斜杠 /。只修改链接，不把全文中的所有反斜杠批量替换掉；代码、Windows 命令和数学公式可能需要反斜杠。

    通过拖拽、截图或粘贴插入图片后，确认图片确实被复制到文章目录，保存 .md，再用 git status 检查图片也被识别为项目文件。发给同事复用文章时，应提供整个文章目录，不能只提供一个 .md。

    7.4 提示块与公式写法¶

    本项目支持以下写法，最后均须检查网页效果：

    > [!note]
>
> 这里填写说明。

行内公式：$L = 3 + L_c$。

独立公式：

$$
L = 5 + (B_2 \Vert B_3)
$$

    标准名称使用书名号，例如 《标准名称》，不要写成 <<标准名称>>，避免被 Markdown 解释成 HTML 而导致文字缺失。

    8. 修改 mkdocs.yml，让文章进入导航¶

    8.1 找到 nav 区域¶

    用编辑器打开项目根目录的 mkdocs.yml，找到 nav:。日常新增文章通常只修改这个区域，保留主题、搜索插件、图片／公式资源和 Markdown 扩展配置。

    目前导航结构如下，路径均对应实际存在的页面：

    nav:
  - 首页:
      - 快速开始: index.md
      - 维护参考: maintenance/维护参考/维护参考.md
  - 密码算法:
      - 章节概览: algorithm/index.md
  - 密码协议:
      - 章节概览: protocol/index.md
  - 密码产品:
      - 章节概览: product/index.md
      - 智能密码钥匙:
          - APDU解析: product/智能密码钥匙/APDU解析/APDU解析.md
  - 密码测评:
      - 章节概览: assessment/index.md
      - 测评基础:
          - 文章编写示例: assessment/测评基础/文章编写示例/文章编写示例.md

    8.2 给现有二级分类增加文章¶

    完成第 7 节的示例文章后，在现有“智能密码钥匙”下加入一行，保持 APDU 文章和其他章节条目：

      - 密码产品:
      - 章节概览: product/index.md
      - 智能密码钥匙:
          - APDU解析: product/智能密码钥匙/APDU解析/APDU解析.md
          - "GBT35291-2017 信息安全技术 智能密码钥匙应用接口规范": product/智能密码钥匙/GBT35291-2017信息安全技术智能密码钥匙应用接口规范/GBT35291-2017信息安全技术智能密码钥匙应用接口规范.md

    这是 nav 中“密码产品”部分的局部示例，不是整个配置文件。 不要把它粘贴到文件开头或末尾另建一个 nav，也不要把同事的文章条目删除。

    8.3 新增一个有文章的二级分类¶

    例如已经创建 docs/algorithm/对称密码算法/SM4算法笔记/SM4算法笔记.md 后，才可以在“密码算法”中登记：

      - 密码算法:
      - 章节概览: algorithm/index.md
      - 对称密码算法:
          - SM4算法笔记: algorithm/对称密码算法/SM4算法笔记/SM4算法笔记.md

    该 SM4 路径也是编写示意，不是当前已有文章。只添加你实际创建的文件，并同步更新章节概览 docs/algorithm/index.md 中的文章链接；其他章节同理。

    8.4 路径和缩进的检查规则¶

    • YAML 用空格缩进，不用 Tab。照现有格式保持同层对齐，子项比父项更深；nav 下第一层 - 前为两个空格。
    • 冒号后保留空格；导航标题包含冒号等符号时，用双引号包住标题。
    • 导航路径相对于 docs/，所以写 product/.../文章.md，不写 docs/product/.../文章.md，也不以 / 开头。
    • 路径使用 /，不能使用 \。目录名、文件名、标准年份和大小写逐字匹配。
    • 改文件名或移动文章时，同时修改 nav、章节概览链接、其他文章链接及文章内的图片路径。
    • 不通过删除整个分类来解决导航错误，不保留指向不存在文件的条目。

    可以用 PowerShell 检查示例文件存在与否：

    Test-Path -LiteralPath "docs\product\智能密码钥匙\GBT35291-2017信息安全技术智能密码钥匙应用接口规范\GBT35291-2017信息安全技术智能密码钥匙应用接口规范.md"

    应输出 True；如果是 False，先修正路径。导航的相对路径规则见 MkDocs 文档说明。

    9. 必须完成：本地构建与 serve 检查¶

    本地检查在准备提交的个人分支上进行。先保存所有 Markdown、图片和 YAML 文件。

    9.1 检查在线版构建¶

    下面第一条命令清除当前终端可能遗留的离线模式，不会删除文件：

    Remove-Item Env:OFFLINE -ErrorAction SilentlyContinue
.\.venv\Scripts\python.exe -m mkdocs build --strict

    终端应显示构建完成。如果出现 ERROR、找不到导航文件、无效图片链接或严格模式中止，先修复再继续，不跳过报错。

    9.2 检查离线版构建¶

    仓库的 GitHub Actions 还会检查离线版，因此上传前也要执行：

    $env:OFFLINE = "true"
.\.venv\Scripts\python.exe -m mkdocs build --strict --site-dir site-offline
Remove-Item Env:OFFLINE -ErrorAction SilentlyContinue

    离线版构建无误后，再进行在线本地预览。上面最后一条命令恢复本终端的默认在线模式；即使构建报错，也先执行这一条再排查。需要检查离线包时，可以用浏览器打开生成的 site-offline/index.html。

    9.3 启动本地服务¶

    .\.venv\Scripts\python.exe -m mkdocs serve

    服务会占用当前终端并打印访问地址，保持它运行，在浏览器中打开打印的完整地址。本项目默认地址为：

    http://127.0.0.1:8000/GM-crypto-assessment-wiki/

    如果 8000 端口已被占用，停止本次启动，然后使用：

    .\.venv\Scripts\python.exe -m mkdocs serve --dev-addr 127.0.0.1:8001

    此时使用终端打印的 8001 地址。不要只打开 http://127.0.0.1:8000/ 而遗漏网站路径前缀。

    9.4 逐项检查网页¶

    • 首页和四个章节可以打开，文章出现在正确章节与二级分类下。
    • 点击文章导航可以打开正文，没有 404，也没有把真实标准名称指向空白测试页。
    • 一级标题写明编号与完整名称，作者、日期、来源和条款信息已经填写。
    • 搜索文章标题、标准编号或正文关键词能找到相应页面；搜索内容不包含 .md 扩展名。
    • 每张图片都能显示；表格、列表、代码、提示块和公式的排版符合预期。
    • 浏览器缩窄后正文仍可阅读；代码或宽表格可以在各自区域滚动。
    • 页面文字没有因 Markdown 或 HTML 写法而丢失；Typora 中正常不代表网页中也正常。
    • 终端没有需要处理的构建报错。修改文件后确认自动重建完成，并刷新页面重新检查。

    检查结束后，在运行服务的终端按 Ctrl+C 停止服务，再执行 Git 提交命令。没有实际启动服务并打开页面检查，不得 push。

    10. Git 提交、同步、push 和合入发布¶

    10.1 查看并暂存本次文件¶

    git branch --show-current
git status
git diff -- mkdocs.yml
git diff -- "docs/product/智能密码钥匙/GBT35291-2017信息安全技术智能密码钥匙应用接口规范/GBT35291-2017信息安全技术智能密码钥匙应用接口规范.md"

    确认仍在自己的 docs/... 分支上。新文件首次尚未被 Git 跟踪时，git diff 不会展示它的内容，需用编辑器检查，再暂存并查看 git diff --staged。

    以下命令会把整篇文章目录下的 .md、图片和附件一起加入暂存区，并加入导航配置：

    git add -- "docs/product/智能密码钥匙/GBT35291-2017信息安全技术智能密码钥匙应用接口规范" "mkdocs.yml"

    如果也更新了对应章节概览，额外暂存：

    git add -- "docs/product/index.md"

    检查待提交内容：

    git diff --staged --stat
git diff --staged
git status

    文件列表应只包含本次计划上传的内容。图片文件也必须在列表中；不能只暂存 .md。不确定其他改动用途时，不直接使用 git add . 把整个工作区全部暂存。

    10.2 创建本地提交¶

    git commit -m "docs: 添加 GBT35291-2017 智能密码钥匙接口规范笔记"
git log -1 --oneline
git status

    提交说明应反映真实变更，例如“修正 APDU 图片路径”“补充 SM4 工作模式笔记”。commit 只保存到本机，尚未上传到 GitHub。

    若提示没有暂存内容，先确认是否漏做 git add，或内容已经提交；不要为了产生新提交随意修改文件。

    10.3 推送前同步同事更新¶

    提交完成且工作区干净后，仍在个人分支执行：

    git fetch origin
git merge --no-edit origin/main
git status

    fetch 获取远端更新；merge 把最新 main 合入当前个人分支，--no-edit 避免为自动生成的合并说明打开编辑器。若出现冲突，按第 12 节处理后才能继续。

    如果合并引入了变更或手动解决了冲突，重新执行第 9 节的构建和 serve 检查。必须保证检查过的是推送时的最终内容。如果返回 Already up to date 且内容未变，可沿用刚才的检查结果。

    10.4 推送个人分支¶

    将分支名替换为第 6 节实际创建的名称：

    git push -u origin docs/zhangsan-gbt35291-2017
git status

    -u 建立与远端分支的关联；同一分支后续补充提交可用 git push。看到 rejected、fatal、error 等失败信息时，按第 12 节在群里同步并排查，不能按上传成功处理。

    10.5 发起 Pull Request¶

    打开源码仓库，通过 Compare & pull request 或 Pull requests → New pull request 创建合并请求：

    1. base 选择 main，compare 选择自己刚推送的分支。
    2. 标题写清新增或修改的文章。
    3. 描述写明文章分类、变更内容，说明已完成在线／离线构建及 serve 浏览器检查。
    4. 提交 Pull Request，将链接提供给维护者审核；需要补充时在同一分支修改、重新检查、提交和 push，PR 会更新。
    5. 等待检查通过和维护者合入，不在日常文章更新中自行覆盖 main 或直接运行 mkdocs gh-deploy。

    可以使用以下 PR 描述模板：

    文章：GBT35291-2017 信息安全技术 智能密码钥匙应用接口规范
分类：密码产品 / 智能密码钥匙
变更：新增学习笔记、随文图片，更新导航与章节概览
验证：在线严格构建通过；离线严格构建通过；已用 serve 检查导航、正文、图片与搜索

    10.6 确认发布并更新本机 main¶

    个人分支 push 成功不等于网站已经更新。 本仓库在 PR 阶段执行文档检查，合入 main 后再由 GitHub Actions 构建并发布在线版。查看仓库 Actions 中的“文档检查与发布”，确认检查及发布成功，再打开在线知识库检查自己的文章。

    若 Actions 失败，先在协作群同步失败任务链接和报错，修复后按相同流程上传；不要因为 push 成功就结束检查。

    合入成功后，在工作区干净的前提下执行：

    git switch main
git pull --ff-only origin main
git status

    下一篇文章再新建新的个人分支，不继续往已经合入的旧分支追加不同任务。

    11. 更新已有文章¶

    更新已有文章也从第 6 节开始同步 main 并创建新分支，然后修改原文章目录中的 .md 和图片。保留作者与来源信息，更新日期，并在“更新记录”中说明改动。

    • 只修改正文或替换同名图片，且文章路径未变时，不需要额外添加一个导航条目。
    • 修改文章标题、文件名、目录或标准年份时，检查并同步修改导航和所有相关链接。
    • 同一个标准发布新年份版本时，建立新目录保存新版本笔记，不覆盖旧版本记录。
    • 移动或删除已有文章前，与维护者确认影响的链接；不把“删掉报错文件”作为修复方法。

    随后仍需完成本地构建、serve 检查、暂存、提交、同步、push、PR 和发布确认。

    12. push 失败、合并冲突与常见问题¶

    12.1 push 失败先在群里同步¶

    先保留完整报错，发送协作消息，不删除 .git、文章或图片，不用 git push --force 覆盖远端历史。

    【文档上传失败】
作者：姓名
文章：编号与名称
分支：docs/姓名-任务名
本地提交：填写 git log -1 --oneline 的结果
本地检查：说明在线／离线构建及 serve 检查结果
失败命令：填写实际执行的 git push 命令
报错摘要：复制关键错误信息
当前处理：本地文件和提交已保留，正在检查网络／权限／分支更新，需要维护者协助确认

    群消息不附带密码、访问令牌或含凭据的远端地址。失败原因确认并修复后，再同步重试结果与 PR 链接。

    12.2 基础排查命令¶

    以下命令不修改文章内容，用于确认仓库、分支和本地提交：

    git status
git branch --show-current
git remote -v
git log -1 --oneline
git ls-remote origin
    现象 检查与处理
    Could not resolve host、超时或连接失败 检查网络和仓库地址；可执行 Test-NetConnection github.com -Port 443 辅助排查。保留本地提交，恢复网络后再推送。
    Authentication failed、401、403、没有写入权限 确认登录的是已获授权的 GitHub 账号，请维护者检查仓库权限，并按凭据管理器提示重新认证。
    Repository not found 检查 git remote -v 中的仓库地址与账号权限，不直接改成陌生仓库。
    non-fast-forward、fetch first、rejected 远端相应分支可能已更新，先获取并合并远端内容，不强推。步骤见下一节。
    分支保护拒绝直接推送到 main 推送自己的分支并发起 PR，请维护者处理合入。
    push 成功，网页没有更新 查看 PR 是否合入 main、Actions 是否成功及是否有浏览器缓存，不把个人分支推送当作发布完成。
    找不到 mkdocs 或 Python 依赖 确认在项目根目录，使用 .venv 的完整命令，重新安装 requirements.txt 中的依赖。
    nav 提示找不到文件或页面 404 比较 docs 下真实路径与 YAML 路径，检查目录名、标准年份、大小写及 /，修复后重建。
    图片在 Typora 正常，在网页缺失 检查图片是否在文章目录并已暂存；检查相对路径、/、大小写和真实文件名。
    8000 端口被占用 使用第 9 节的 8001 启动命令，并访问终端打印的新地址。

    12.3 远端个人分支已更新¶

    仅在 push 提示自己这个远端分支已存在新提交时执行。先确认本机改动已提交，仍在该个人分支；示例中的远端分支必须换成报错涉及的实际名称：

    git fetch origin
git merge --no-edit origin/docs/zhangsan-gbt35291-2017
git status

    合并成功后重新完成本地构建和 serve 检查，再执行：

    git push origin docs/zhangsan-gbt35291-2017

    如果远端 main 也有更新，还需按第 10.3 节同步。不要把获取别人的提交替换成强制覆盖。

    12.4 处理 merge 冲突¶

    多人修改 mkdocs.yml 时，可能出现 CONFLICT。先在群里说明涉及的文件，再用下面的命令查看：

    git status

    用编辑器打开冲突文件，定位这些标记：

    冲突标记 含义
    <<<<<<< HEAD 当前分支内容的开始
    ======= 两个版本内容的分隔
    >>>>>>> origin/main 被合并分支内容的结束；分支名也可能是个人分支

    确认双方改动的目的，保留需要的文章和导航条目，整理成一份有效内容，并删除全部冲突标记。对 YAML 特别检查四个章节是否完整、缩进是否正确、是否有重复条目、是否误删同事的文章。

    例如只有 mkdocs.yml 发生冲突，解决并保存后：

    git add -- "mkdocs.yml"
git status
git commit --no-edit

    还有其他冲突文件时，逐个解决并用 git add -- "实际文件路径" 暂存，直到 git status 不再显示未合并文件，才执行合并提交。完成后重新运行构建和 serve，通过后再 push。

    无法确定如何合并时，先请求维护者协助。若决定取消当前 merge，在编辑合并结果前优先执行：

    git merge --abort

    它用于退出当前合并，回到合并前状态；不要用删除仓库、强推或 git reset --hard 代替冲突处理。Git 的合并及取消规则见 Git 官方 merge 说明。

    13. 上传前验收与日常流程速查¶

    13.1 作者上传前勾选¶

    • 文章归属四个章节之一，二级分类正确。
    • 每篇文章有自己的目录，.md、图片和附件都在其中。
    • 标准类文章的编号、完整名称、年份、作者、更新日期及来源已填写。
    • 文件名、目录、正文标题和导航中的标准编号一致，没有虚构或未确认的版本。
    • Markdown 图片路径和 YAML 路径统一使用 /，没有本机绝对路径。
    • 图片与文章一起暂存，导航指向真实文件；章节概览中的链接同步更新。
    • 在线版和离线版严格构建通过。
    • 已对最终内容实际启动 serve 并检查正文、图片、导航和搜索。
    • Git 提交只包含本次内容，个人分支已同步同事更新。
    • push 成功后已发起 PR；失败时已在协作群同步并保留本地提交。

    13.2 每次操作顺序¶

    以下用于已经完成首次环境配置的同事。路径、分支名和提交说明替换为自己的实际内容，各项成功后才进行下一项：

    # 1. 工作区干净时同步主分支，建立新的个人分支
git status
git switch main
git pull --ff-only origin main
git switch -c docs/zhangsan-gbt35291-2017

# 2. 新建或编辑文章、整理随文图片、修改 mkdocs.yml 和章节概览
# 按第 7、8 节操作并保存文件

# 3. 检查在线版和离线版；出现错误先处理
Remove-Item Env:OFFLINE -ErrorAction SilentlyContinue
.\.venv\Scripts\python.exe -m mkdocs build --strict
$env:OFFLINE = "true"
.\.venv\Scripts\python.exe -m mkdocs build --strict --site-dir site-offline
Remove-Item Env:OFFLINE -ErrorAction SilentlyContinue

# 4. 启动服务，在浏览器实际检查；完成后 Ctrl+C
.\.venv\Scripts\python.exe -m mkdocs serve

# 5. 暂存自己的文章、图片、导航及已修改的章节概览
git add -- "docs/product/智能密码钥匙/GBT35291-2017信息安全技术智能密码钥匙应用接口规范" "mkdocs.yml" "docs/product/index.md"
git diff --staged --stat
git diff --staged
git commit -m "docs: 添加 GBT35291-2017 智能密码钥匙接口规范笔记"

# 6. 获取并合并同事更新；有变更或冲突处理后重新完成第 3、4 步
git fetch origin
git merge --no-edit origin/main
git status

# 7. 推送自己的分支；失败先在群里同步
git push -u origin docs/zhangsan-gbt35291-2017

# 8. 在 GitHub 发起 PR，合入后检查 Actions 和在线页面

    本代码块是操作顺序说明，不要整段一次执行：serve 需要人工打开浏览器检查，合并可能需要处理冲突，任何失败都需要停下来排查。

    13.3 维护者验收¶

    维护者合入前检查章节与文章目录规范、标准编号与名称、引用出处、随文图片、导航变更和 PR 构建结果。合入后确认发布任务成功，在线页面能打开；异常时在群里同步问题及处理结果。

    工具细节可查阅 Git 官方文档、MkDocs 文档维护说明、Typora 图片说明和 WinGet 安装命令说明。实际项目操作以本手册的目录、分支、导航和上传流程为准。
